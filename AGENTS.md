# Kingfisher — a guide for the next coding agent

Everything above this line is generated by `next dev`. Leave it alone; it is
re-added if removed, and committing it with your work keeps the tree clean.

## What Kingfisher is

A chess research workstation for strong players: analysis, studies, opening
preparation, a repertoire, a game database, an opening explorer over several
reference sources, native and browser engines, and a review workflow for the
player's own decisions. It runs as a Next.js application in the browser, with an
optional local **companion** process for the things a browser cannot do — native
UCI engines, SQLite databases, and tablebase probing.

Read `ARCHITECTURE.md` before making a structural change. This file is the map;
that one is the territory.

## Dependency direction

```
app/ → features/ → stores/ → engine/ database/ persistence/ → chess/
```

Dependencies point **downwards only**.

- `src/chess/` is the domain. **No React, no I/O, no imports from above.** It is
  the most valuable code in the repository and is fully unit tested.
- `src/engine/`, `src/database/`, `src/persistence/` define capability
  interfaces and their implementations. `persistence/` is the only place that
  names IndexedDB.
- `src/stores/` is the only place the domain and the capabilities are wired
  together.
- `src/features/` renders. Components never contain chess rules or protocol
  handling.

## The rules that are not negotiable

**The chess.js boundary.** `src/chess/position.ts` is the only module allowed to
import `chess.js`. Swapping the rules implementation must mean changing that one
file. Do not reach for `chess.js` anywhere else, and do not trust it to validate
a position — Kingfisher's own FEN parser rejects what the library tolerates. See
`src/chess/variant-contract.test.ts` and ADR 0047 for why: a castling right is a
claim about where two pieces stand, and an unchecked claim produced an illegal
move offered as legal.

**Canonical position identity.** Two positions reached by different move orders
are the same position. `positionKey()` is that identity, and it is what makes
transpositions, "have I been here before?", repertoire lookup and the explorer
agree with each other. Never key chess data on a move sequence when the position
is what you mean.

**The game tree is immutable.** A move node knows the position it was played in.
Edits produce a new tree; nothing mutates a node in place.

**One board.** There is a single board rendering architecture used by every
surface — analysis, studies, openings, repertoire, preparation, review,
calculation, training, endgame, model games, opening files, PV preview, position
setup and play-from-here. If you need a board, use it. A second board renderer
is a bug.

**Standard chess only.** Kingfisher does not play Chess960, and it refuses
positions it cannot play rather than guessing. Engine Chess960 capability is
_recorded_ because it is a fact about the engine, not because the rules code
supports it.

## Persistence

Autosave writes a draft before it writes a document, so a crash costs at most
the draft. Chapters carry a **revision**; a cross-tab update that would lose
local work is reported as a conflict rather than applied. Migrations are
forward-only and every historical schema has a fixture.

Backups are portable JSON. **Every store holding work a person authored must be
in `PORTABLE_STORES`** — that list has been wrong before, and a backup that
silently omits a store is indistinguishable from a complete one until a restore.
Reference _pack contents_ are deliberately excluded; pack _metadata_ is not, so a
restore can say which sources to reinstall.

## Databases and providers

Collections sit behind a repository abstraction and sources behind a provider
abstraction, so IndexedDB, SQLite via the companion, reference packs and remote
services are all the same shape to the rest of the application.

**Provenance is never lost.** A source's numbers are labelled with that source.
Sources are never silently merged, and a remote failure must never blank local
evidence.

**The move invariant:** a copy is verified at the destination before the source
is deleted. Never the other way round.

## Engines

UCI output carries **no request identity**. Every line an engine writes is
attributed to whatever search the session believes is running, so the session —
not the caller — owns the boundary between searches. Before any engine result
enters UI state it must carry session, position and engine identity.

A process that fails to acknowledge a stop is not reused; it is failed. This is
deliberate and load-bearing: reusing it would let its late `bestmove` be read as
evidence about the next position. See `src/engine/uci-adversarial.test.ts`.

Capability rows are **produced by interrogation, never inferred from a name**.
`npm run engines:verify` launches each engine and asks it. An engine is Ready
only when it handshakes _and_ completes a real search — for a neural engine that
second condition is the whole condition, because Lc0 handshakes happily with no
weights at all.

Managed native engines are downloaded against a recorded digest and run with the
user's own operating-system permissions. **They are not sandboxed.** Do not
describe them as if they were.

## Reference data and provenance

Opening names come from a licensed upstream classification. Do not invent names
past what the source classifies — a deep position inherits the last named
opening above it instead of acquiring a new one. Variation briefs are authored or
deterministic, never generated at runtime and presented as theory.

Every third-party dataset and asset is recorded in `THIRD_PARTY_DATA.md` and
`THIRD_PARTY_ASSETS.md`. Add to them when you add a source.

## Building a reference pack

`scripts/build-reference-pack.mjs` builds every pack from an upstream archive:
download or stream, verify against the publisher's own digests, replay through
Kingfisher's rules code, aggregate by position, shard, compress, write a
manifest. Packs are declared in `scripts/reference/packs.mjs`.

Two things about the archives will waste your afternoon if you do not know them.

They are **seekable zstd**: real frames with skippable frames interleaved
throughout. Piping one into `createZstdDecompress()` fails at byte zero, and
dropping only the leading skippable frames gets past that and then stops
_silently_ at the next one — a build that succeeds and writes a pack a fraction
of the right size. Use `zstdFrameStream()`, which walks the frames.

And a game must be **rejected on its headers** when the source is large.
`readGames(file, { accept })` decides from the tags before the movetext is
tokenised. The standard database holds about ninety million games a month and
the high-rated pack keeps one in two hundred and fifty; without early rejection
the build is not slow, it is infeasible.

## Interoperability

`src/database/encroissant/` reads another program's database. Two rules:

Kingfisher **never writes to it**. It belongs to a program that may be running.

And the move encoding is **verified, not assumed**. En Croissant stores a move
as an index into the list its rules library generates, so a decoder that orders
that list differently returns a move that is legal, plausible and wrong, with
nothing downstream able to tell. `shakmaty-order.ts` reproduces that ordering and
`decode.test.ts` checks it against a database En Croissant actually wrote, using
that program's own decoding as the reference. If you touch the ordering, that
test is the one that must fail first.

## Testing expectations

- `src/**/*.test.ts` — unit and integration, Vitest, node environment.
- `e2e/*.spec.ts` — Playwright, **`retries = 0`**. A flaky green is not green.
- Fixtures, fuzz, migration, chaos and benchmark suites live alongside these.

**A test that cannot fail proves nothing.** For any regression test that matters,
revert the implementation once and confirm the test actually fails. Phase history
has repeatedly turned up passing tests that asserted the wrong thing — selectors
matching the wrong element, expectations derived from the same constant as the
implementation, and assertions that passed vacuously.

Do not mock the thing under test. Stub the boundary — the transport, the global,
the HTTP client — and run the real class.

## Two rules about honesty

**Do not fake data.** A feature that cannot be built honestly is left visible and
disabled rather than mocked. No fictional number may reach a chess judgement. A
synthetic dataset is not a substitute for a real one, and must not be reported as
though it were.

**Do not fake capabilities.** Never claim an engine, a source or an integration
was verified unless it was actually run. "Live tested" means a real round trip
happened. If it could not be run in your environment, say exactly that.
